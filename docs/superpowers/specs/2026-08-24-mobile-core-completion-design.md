# 스캐치북 모바일 핵심 완성 디자인

## 목표

현재 알파 버전의 핵심 흐름을 모바일 Chrome에서 처음부터 끝까지 사용할 수 있는 수준으로 완성한다. 생성자는 본인 그림과 선택적 참고 사진을 저장하고, 친구는 공개 링크에서 참고 사진을 보며 그림을 제출하고, 생성자는 실제 그림을 관리해 BEST 1~4가 포함된 1080×1440(3:4) PNG를 내려받는다.

## 범위

### 포함

- 생성자 본인 그림 작성 및 저장
- 선택적 참고 사진 업로드·교체·삭제·사용 여부 설정
- 친구 그림판의 그림/참고사진/편집 탭
- 한 손가락 그리기와 참고 사진 확대·축소·이동
- 펜, 지우개, 색상, 굵기, 실행 취소, 다시 실행, 전체 삭제
- 빈 그림 제출 방지와 모바일 키보드·오류 상태 처리
- 공개 페이지의 실제 본인 그림 및 친구 그림 표시
- 관리 화면의 실제 이미지, 공개·숨김, 삭제, BEST 1~4 지정·해제
- 실제 이미지가 합성된 Instagram 공유용 1080×1440(3:4) PNG
- 생성·친구 제출·관리·결과물 흐름의 Firebase 에뮬레이터 E2E 테스트
- Chrome 320px, 390px, 모바일 가로 화면 시각·동작 검증
- 이미지 생성 기능으로 제작한 프로젝트 파비콘 적용

### 제외

- 운영자 관리자 페이지
- 실결제 연동
- Firebase App Hosting 배포와 커스텀 도메인
- App Check, CAPTCHA, 고급 Rate Limit
- 실제 iPhone Safari 및 Android 실기기 검증

## 모바일 UX

- 모든 주요 터치 대상은 최소 44×44px로 제공한다.
- 고정 CTA와 하단 도구 영역에는 `safe-area-inset-bottom`을 적용한다.
- 모바일 세로 화면을 기본으로 하고 320px에서도 가로 스크롤이 생기지 않게 한다.
- 캔버스는 브라우저 스크롤과 그리기 제스처가 충돌하지 않도록 `touch-action`을 기능별로 제어한다.
- 참고 사진은 그림 아래 별도 레이어로 표시하며 최종 저장 PNG에는 그림 레이어만 포함한다.
- 생성과 제출 폼은 모바일 키보드가 열린 상태에서도 오류와 제출 버튼을 확인할 수 있어야 한다.
- 숨김·삭제·BEST 같은 관리 작업은 한 카드에 과밀하게 나열하지 않고 선택 메뉴 또는 하단 작업 영역으로 점진적으로 공개한다.

## 생성자 흐름

1. 이름 또는 애칭을 입력한다.
2. 선택적으로 참고 사진을 등록한다.
3. 본인 스케치를 그린다.
4. 스케치북을 생성하면 Firestore 문서, 본인 그림, 참고 사진을 서버에서 원자적으로 연결한다.
5. 관리 세션과 별도로 복구 가능한 관리 토큰 링크를 한 번 제공한다.

본인 그림은 `sketchbooks/{sketchbookId}/owner/original.png`, 참고 사진은 `sketchbooks/{sketchbookId}/reference/source`에 저장한다. Firestore 스케치북 문서에는 `ownerDrawingPath`, `referenceImagePath`, `referenceImageEnabled`를 기록한다.

## 친구 흐름

1. `/s/{publicId}`에서 생성자 본인 그림과 공개된 친구 그림을 본다.
2. `친구 스케치 하기`를 누르면 `/s/{publicId}/draw`로 이동한다.
3. 참고 사진이 활성화된 경우 참고사진 탭에서 위치·확대 배율을 조절한다.
4. 그림 탭에서 그린 뒤 편집 탭 또는 제출 영역에서 이름과 선택 메시지를 입력한다.
5. 빈 캔버스가 아니며 한도가 남아 있을 때만 서버가 Storage와 Firestore에 저장한다.

## 관리 흐름

- 관리 화면은 모든 친구 그림의 실제 이미지를 표시한다.
- 공개·숨김 전환, 삭제, BEST 지정·해제를 서버 권한 검증 후 처리한다.
- BEST 순위는 스케치북마다 1~4가 중복되지 않는다.
- 삭제된 그림은 Firestore 상태를 `DELETED`로 바꾸고 Storage 파일은 비동기 또는 즉시 정리한다.
- 관리 링크는 쿠키가 없는 브라우저에서 토큰을 검증한 뒤 새 관리 쿠키로 교환하고 URL에서 토큰을 제거한다.

## 스토리 이미지

- 공유 이미지 캔버스 크기는 정확히 1080×1440이다.
- BEST 1을 크게 배치하고 BEST 2~4를 하단 3열에 배치한다.
- 선정된 BEST가 네 장보다 적으면 빈 슬롯을 종이 질감의 안내 상태로 표시한다.
- 실제 공개 URL을 이미지 하단에 표시한다.
- 생성은 브라우저 Canvas에서 수행하며 외부 분석·변환 서비스로 사용자 이미지를 전송하지 않는다.

## 파비콘

- 이미지 생성 기능으로 새 래스터 이미지를 만든다.
- 심볼은 손으로 그린 듯한 펼친 스케치북과 연필이며 글자는 넣지 않는다.
- 아이보리 종이 배경, 짙은 잉크 선, 절제된 블루그레이 한 점만 사용한다.
- 작은 크기에서도 읽히도록 세부 장식을 줄이고 중앙에 크게 배치한다.
- 생성 원본을 프로젝트에 보관하고 `src/app/icon.png`로 적용한다.

## 서버·보안

- 브라우저는 Firestore와 Storage를 직접 쓰지 않고 Next.js Route Handler만 사용한다.
- 이미지 형식은 PNG, JPEG, WEBP로 제한하고 디코딩 후 크기를 다시 검사한다.
- 관리 작업은 `HttpOnly`, `SameSite=Lax`, `Secure` 관리 쿠키와 토큰 해시 검증을 통과해야 한다.
- 삭제·BEST·한도 증가는 Firestore Transaction으로 일관성을 유지한다.
- 기본 Firebase 보안 규칙은 계속 모든 클라이언트 접근을 거부한다.

## 테스트와 완료 기준

- 도메인·세션·이미지 검증 로직은 Vitest에서 실패 테스트를 먼저 작성한다.
- Firebase Rules 테스트에서 직접 Firestore·Storage 접근이 계속 거부되어야 한다.
- Playwright E2E가 생성 → 공개 링크 → 친구 그림 → 관리 → BEST → PNG 다운로드를 검증한다.
- Chrome에서 320×700, 390×844, 844×390 뷰포트를 한 번의 검증 패스로 확인한다.
- 터치 대상, safe area, 가로 넘침, 캔버스 입력, 모바일 키보드 인접 UI를 점검한다.
- 린트, 전체 테스트, 프로덕션 빌드가 모두 성공해야 한다.

## 비용 보호

- 사용자 이미지 입력은 압축·크기 제한을 거친다.
- 공개 이미지 응답은 캐시를 사용한다.
- 에뮬레이터 기반 E2E를 우선해 운영 Firebase 읽기·쓰기 사용량을 만들지 않는다.
- App Hosting 최대 인스턴스 1 설정을 유지한다.
