# 프로젝트 전체 하드닝 설계

## 목표

스캐치북의 기존 제품 정체성과 공개 인터페이스를 유지하면서 다음 문제를 해결한다.

1. 키보드·스크린 리더 사용자가 친구 그림 제출을 완료할 수 없는 문제
2. 복구 불가 관리 PIN의 오타 및 브라우저 초안 저장 위험
3. 공개 생성·제출 API의 운영 설정 누락과 확장 시 요청 제한 약화 위험
4. 작은 화면에서 랜딩 CTA가 첫 화면 밖으로 밀리는 문제
5. 실제 친구 그림보다 빈 BEST 슬롯이 먼저 노출되는 문제
6. 관리·저장소·스타일 파일의 책임 집중과 전체 E2E 테스트 드리프트

## 작업 분해

작업은 두 하위 프로젝트로 나눈다.

### A. 출시 하드닝

사용자와 운영 환경에 직접 영향을 주는 변경이다. PIN, 접근성 대체 입력, 공개 화면 위계, 운영 보안 설정, 회귀 테스트를 포함한다.

### B. 유지보수성 개선

출시 하드닝이 통과한 뒤 동작을 바꾸지 않고 파일 책임을 분리한다. 관리 대시보드, 스케치북 저장소, 전역 CSS를 대상으로 한다.

두 하위 프로젝트는 각각 독립적으로 테스트 가능한 커밋 단위를 가지며, B는 A의 검증된 동작을 기준선으로 사용한다.

## 사용자 경험 설계

### 관리 PIN

- 생성 폼에 `관리용 비밀번호 확인` 필드를 추가한다.
- 두 PIN이 다르면 서버 요청 전에 확인 필드 가까이에 오류를 표시하고 포커스를 이동한다.
- 생성 초안에는 이름, 힌트, 선택적 그림만 저장하고 PIN과 PIN 확인값은 저장하지 않는다.
- 기존 초안에 남아 있는 PIN은 불러오지 않고 다음 저장 시 제거한다.
- 생성 완료 화면에는 `친구에게 공유하기`를 주 행동으로, `내 스캐치북 관리하기`를 보조 행동으로 제공한다.
- 공유는 기존 Web Share API와 클립보드 fallback 패턴을 재사용한다. 공유 실패 시 사용자가 다시 시도할 수 있는 문구를 보여준다.

### 접근 가능한 그림 제출

- 포인터 캔버스는 기존 동작을 유지한다.
- 그림 편집 진입점 옆에 키보드로 접근 가능한 `이미지로 가져오기` 보조 행동을 제공한다.
- PNG, JPEG, WebP 파일을 받아 정사각형 흰 캔버스 안에 비율을 유지해 배치한다. 서버의 기존 이미지 최적화와 검증은 그대로 적용한다.
- 브라우저에서 읽을 수 없는 파일, 지원하지 않는 형식, 지나치게 큰 파일에는 입력 가까이에 복구 가능한 오류를 표시한다.
- 가져온 이미지는 기존 미리보기, 다시 편집, 제출 흐름을 그대로 사용한다.
- 캔버스는 설명 텍스트와 연결하고 포인터 그리기가 선택 사항임을 스크린 리더에 전달한다.
- 펜과 지우개 버튼은 `aria-pressed`로 상태를 전달한다.
- 그림 가져오기·확정·초기화 상태는 `aria-live="polite"` 영역에서 알린다.

이미지 가져오기는 포인터 사용이 어려운 사용자가 외부의 접근 가능한 도구로 만든 그림을 제출할 수 있는 대체 경로다. 키보드 방향키로 자유 곡선을 그리는 별도 편집기는 복잡성과 학습 비용이 커 이번 범위에 포함하지 않는다.

### 랜딩 CTA

- 621px 이상이지만 세로 공간이 짧은 화면에서도 CTA가 첫 화면에 남도록 콜라주 높이와 세로 간격을 유동적으로 줄인다.
- 특정 기기 크기를 추가하는 대신 `100svh`와 `clamp()`를 사용해 사용 가능한 높이에 맞춘다.
- 320×568, 390×667, 390×844에서 제목·대표 이미지·CTA의 순서와 터치 영역을 확인한다.
- 기존 종이·손그림 시각 세계와 650px 단일 책 폭은 유지한다.

### 공개 BEST 섹션

- 실제 BEST 순위가 하나 이상 있을 때만 BEST 섹션을 렌더링한다.
- 렌더링할 때도 선정된 슬롯만 보여주고 빈 `선정 전` 슬롯은 만들지 않는다.
- 친구 그림이 있지만 BEST가 없으면 친구 그림 그리드가 바로 소개 문구 다음에 온다.
- 첫 그림 제출 완료 메시지와 자신의 스케치북 생성 CTA는 유지한다.

## 운영 보안 설계

### App Check 설정 정합성

- 공개 클라이언트 활성화, 사이트 키, 서버 강제 플래그의 조합을 하나의 설정 판별 함수에서 검증한다.
- 세 값이 모두 비활성이면 개발 모드로 동작한다.
- 일부만 활성화된 불완전한 조합은 공개 mutation을 `503`으로 거절하고 서버 로그에는 비밀값 없이 설정 오류 코드만 남긴다.
- 운영 배포에서는 세 설정이 모두 활성화되어야 한다. 배포 전 검증 함수와 문서화된 체크 명령으로 이를 확인한다.
- `apphosting.yaml`에는 비밀값 자체가 아니라 필요한 변수/secret 연결 항목을 명시한다.

운영 환경을 코드만으로 무조건 fail-closed 처리하면 기존 배포가 즉시 중단될 수 있으므로, 설정 조합 검증과 배포 설정을 함께 적용한다. 실제 사이트 키 등록은 저장소 밖의 Firebase 콘솔 작업으로 남긴다.

### 요청 제한

- 현재 단일 인스턴스 메모리 구현은 `PublicMutationRateLimiter` 인터페이스 뒤로 이동한다.
- Route Handler는 저장 방식이 아니라 인터페이스에만 의존한다.
- 현재 `maxInstances: 1` 조건에서는 기존 한도와 동작을 유지한다.
- 다중 인스턴스로 변경할 때 공유 저장소 구현이 없으면 배포 검증이 실패하도록 운영 문서와 테스트 가능한 설정 검사를 추가한다.
- 이번 작업에서 Redis, Cloud Armor, Firestore 카운터 같은 새 운영 의존성은 추가하지 않는다.

### CSP와 의존성

- CSP의 `unsafe-inline`은 Next.js 16의 nonce 적용 영향과 정적 렌더링 비용을 로컬 문서 기준으로 확인한다.
- 기존 정적 페이지와 인라인 스타일을 깨지 않고 제거할 수 있는 항목만 제거한다.
- 안전하게 제거할 수 없으면 허용 범위와 후속 nonce 전환 조건을 보안 문서에 기록하고 추측성 변경을 하지 않는다.
- `npm audit --omit=dev` 결과는 직접/전이 의존성 경로와 실제 사용 경로를 구분한다.
- 파괴적 Firebase Admin 다운그레이드나 검증되지 않은 `overrides`는 적용하지 않는다.
- 안전한 상위 패키지 업데이트가 존재할 때만 lockfile을 갱신한다.

## 유지보수성 설계

### 관리 대시보드

`ManageDashboard`는 다음 경계로 분리한다.

- `ManageHeaderActions`: 친구 홈, 스토리, 공유, 비밀번호, 로그아웃 진입
- `ShareThumbnailSettings`: 썸네일 선택과 저장 상태
- `ManageDrawingCard`: 공개 상태, BEST 순위, 삭제 진입
- `ManagePurchaseDialog`: 상품, 휴대전화번호, 동의, 결제 요청
- `ManageSecurityDialog`: PIN 변경
- `DeleteDrawingDialog`: 그림 삭제와 제출 횟수 복구

네트워크 요청과 최상위 상태는 우선 `ManageDashboard`에 유지한다. 분리된 컴포넌트는 표시와 이벤트 전달에 집중하며, 리팩터링 중 API 형식이나 사용자 문구를 바꾸지 않는다.

### 스케치북 저장소

기존 `repository.ts`의 export를 유지하는 배럴 구조를 사용한다.

- `repository-read.ts`: 스케치북·그림 조회와 변환
- `repository-drawings.ts`: 제출 한도, 공개 상태, BEST 순위
- `repository-management.ts`: PIN 세션과 시도 제한
- `repository-deletion.ts`: 삭제 작업과 정리 상태
- `repository.ts`: 호환성을 위한 re-export

Firestore 컬렉션 경로, 트랜잭션 범위, 오류 클래스, 공개 함수 시그니처는 변경하지 않는다.

### 스타일

`globals.css`는 cascade 순서를 유지한 채 다음 파일로 나눈다.

- `styles/foundation.css`: 토큰, reset, 공용 버튼·입력·다이얼로그
- `styles/marketing.css`: 랜딩, 정책, 생성
- `styles/sketch.css`: 캔버스와 그리기 도구
- `styles/public.css`: 공개 스케치북과 갤러리
- `styles/manage.css`: 관리·공유·결제
- `styles/admin.css`: 운영자 화면

`globals.css`는 위 파일을 정해진 순서로 import하는 진입점이 된다. 선택자 우선순위와 렌더링 결과를 바꾸지 않는 기계적 이동을 먼저 수행하고, 랜딩·BEST 개선은 해당 파일에서 별도 테스트로 적용한다.

## 데이터 흐름

### 스케치북 생성

1. 사용자가 이름, PIN, PIN 확인값, 선택적 그림을 입력한다.
2. 클라이언트가 PIN 일치 여부를 검증한다.
3. 서버에는 기존 payload 형식대로 PIN 하나만 전송한다.
4. 성공하면 로컬 초안을 제거하고 공개 URL과 관리 URL을 보관한다.
5. 사용자는 공개 URL을 공유하거나 관리 화면으로 이동한다.

### 이미지 가져오기

1. 사용자가 파일 입력을 연다.
2. 클라이언트가 형식과 크기를 확인한다.
3. 이미지를 메모리에서 디코딩해 기존 720×720 캔버스에 `contain` 방식으로 그린다.
4. 기존 확정 로직이 흰 배경 WebP 미리보기를 생성한다.
5. 기존 서버 Route Handler가 다시 디코딩·최적화·용량 제한을 적용한다.

### 공개 mutation 보호

1. 설정 판별기가 App Check 조합을 확인한다.
2. 활성화된 경우 토큰을 검증한다.
3. 요청 제한 인터페이스가 IP와 전역 한도를 검사한다.
4. Zod 검증과 기존 저장 로직이 실행된다.

## 오류 처리

- PIN 불일치는 확인 필드에 연결된 오류로 표시한다.
- 파일 오류는 선택한 파일명을 유지하지 않고 다시 선택할 수 있게 한다.
- 공유 API·클립보드 실패는 관리 URL 이동을 막지 않는다.
- App Check 구성 오류와 사용자 토큰 오류는 각각 `503`, `401`을 유지한다.
- 요청 제한은 기존 `429`와 `Retry-After` 형식을 유지한다.
- 리팩터링된 컴포넌트는 기존 오류 문구와 포커스 복귀 동작을 유지한다.

## 테스트 전략

각 작업은 TDD 순서를 따른다.

### 단위·컴포넌트 테스트

- PIN 확인 불일치, 초안 PIN 제외, 기존 초안 PIN 무시
- 생성 완료 공유 성공·fallback·실패 상태
- 이미지 파일 형식·크기·디코딩 오류·성공 미리보기
- 펜·지우개 `aria-pressed`, 캔버스 설명, live status
- BEST 없음·부분 순위·4개 순위 렌더링
- App Check 설정 조합과 요청 제한 인터페이스
- 분리한 관리 컴포넌트의 이벤트·포커스·오류 상태
- 저장소 export 호환성과 기존 트랜잭션 테스트

### E2E·브라우저 테스트

- 워터마크 팝업을 연 뒤 휴대전화번호와 동의를 입력하도록 기존 E2E를 갱신한다.
- 390×667 랜딩 CTA viewport 검증을 추가한다.
- 이미지 가져오기로 친구 제출을 완료하는 키보드 중심 흐름을 추가한다.
- BEST 미선정 상태에서 빈 슬롯이 보이지 않는지 확인한다.
- 모바일 전체 생성→친구 제출→BEST→스토리→삭제 흐름을 다시 통과시킨다.

### 최종 검증

- `npm test`

- `npm run build`
- `npm run test:e2e -- --project=mobile-chrome`
- Impeccable detector를 변경된 UI 대상에 한 번 실행

## 완료 기준

- P1 접근성, PIN, 운영 설정 문제가 테스트 가능한 형태로 해결된다.
- 실제 BEST가 없을 때 빈 슬롯이 렌더링되지 않는다.
- 390×667에서 랜딩 CTA가 첫 화면 안에 있다.
- 전체 모바일 E2E가 팝업 UI와 일치한다.
- 공개 함수와 API payload가 호환된다.
- 주요 대형 파일의 책임이 분리되고 전체 테스트·빌드가 통과한다.
- 운영자만 수행할 수 있는 Firebase 콘솔 설정은 값 없이 명확히 보고한다.
